# Cards from conversations

Scope: the Pro node, web Conversations and Kanban Loop. No mesh rollout or native iOS feature was added.

## Implementation

- Work conversations create one Running card on the first user message, with the same card/conversation identity. Empty conversations, Zeca and shell conversations are excluded. Title inference uses the existing conversation title with no additional model call; manual card rename locks it. The original first message is preserved, including messages longer than the ledger preview. Runtime exit, cancellation, crash and archive finish a card still on Running; a pending approval stays in To do, and an existing park or manual move is preserved. Continuing reopens it and consumes the standing approval. Manual Done leaves the runtime alive.
- Zeca's web header offers an editable card draft from ten messages, widening by ten to fifty. The latest card's message boundary applies only to the default window. Tool and operational records are excluded, assistant revisions are merged, and attachments use filename markers.
- Inference uses the cheapest configured Anthropic ladder target through the existing logging proxy, 800 output tokens, a 20-second deadline and one retry. Haiku 4.5 has no effort API parameter, so its existing low-cost behavior uses disabled thinking; models supporting effort receive low. Failed inference produces the editable verbatim transcript. The API returns the created To do card with a warning when starting or scheduling fails.
- The UI reuses the board sheet, date/time picker and conversation toast. Source and card links work in both directions, including assistant-message coordinates and unavailable sources. Both creation event shapes are recorded in the conversation ledger.

## Approval completion regression, 9 September 2026

Two live work-session cards were incorrectly moved from To do to Done immediately after the launcher paused for approval. The runtime-exit helper treated every exit as completion, including the approval gate. Archive and startup reconciliation called the same helper.

The helper now preserves approval in To do, repairs older Done cards carrying an approval, preserves cards already moved off Running, and rechecks these decisions after CAS conflicts. Starting a stretch clears the approval. The board CAS rejects Done with a pending approval even when an evidence override is supplied; the HTTP API reports `approval-required`. A deliberate human move can still clear the ask and finish the card.

Five focused regressions cover exit/archive/restart, legacy repair, a concurrent approval winning the completion CAS, existing parks/manual moves, and API/direct-CAS refusal. Four baseline cases failed before the implementation. All 94 relevant tests pass across six suites, including the 17 browser journeys. The new browser journey uses the real gateway, board and conversation HTTP servers with a controlled runtime child: triage hands off to implementation, the launcher pauses in To do, the browser clicks Approve & continue, and implementation starts with the ask cleared. TypeScript passes. An initial browser assertion incorrectly waited for a log event absent from the message endpoint; it now waits for the gateway's actual `advancing` state to settle.
